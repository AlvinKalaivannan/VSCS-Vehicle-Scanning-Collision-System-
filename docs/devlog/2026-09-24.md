### The geometry (P0-T3), in MAT188 terms

Written down here because the point of pair mode is that you can defend this in an
interview.

A rigid transform is a **linear map on homogeneous coordinates**. Write a point as
`p~ = [x y z 1]ᵀ ∈ ℝ⁴`, and

```
T = [ R  t ]      R ∈ SO(3),  t ∈ ℝ³        T p~ = [Rp + t, 1]ᵀ
    [ 0  1 ]
```

The appended 1 and the fourth row exist for exactly one reason: **translation is not a
linear map on ℝ³**, because it moves the origin. Lifting to ℝ⁴ makes it one, and that is
why transforms compose by plain matrix multiplication. Two things fall out and are used
everywhere in the module:

1. **Inversion is free.** `R` is orthogonal, so `R⁻¹ = Rᵀ`. Solving `q = Rp + t` gives
   `p = Rᵀq − Rᵀt`, so `T⁻¹ = [[Rᵀ, −Rᵀt], [0, 1]]`. `invert()` uses this closed form —
   `np.linalg.inv` is both slower and less accurate. The test asserts the closed form
   hits identity to 1e-14, where the generic inverse only manages ~1e-10.
2. **Order matters**, because SO(3) does not commute. The `T_a_b` naming is the guard
   rail: inner subscripts must cancel (`T_a_b @ T_b_c = T_a_c`), and numpy cannot check
   that for you, so the discipline is in every signature.

The `veh` ↔ `cam` convention is now a tested constant rather than a comment. `veh` is
x-forward / y-left / z-up, `cam` is x-right / y-down / z-forward, so

```
cam x (right)   = −veh y        R_CAM_VEH = [ 0 −1  0 ]
cam y (down)    = −veh z                    [ 0  0 −1 ]
cam z (forward) = +veh x                    [ 1  0  0 ]
```

Row *i* is the *i*-th cam basis vector written in veh coordinates, which is precisely
what makes `p_cam = R_CAM_VEH @ p_veh` true. `det = +1` is asserted — a `−1` would be a
reflection, silently swapping left and right.

  (below). Wrote **ADR 0004** and updated `configs/model.yaml`, `configs/risk.yaml` and
  the capture checklist.

**What failed / surprised me:**

- **The sliding door should never have been a joint.** I had it as `prismatic` along x.
  A van's sliding door runs on a *curved* track: it pops outward, travels rearward, then
  settles back. A straight prismatic joint would be wrong by roughly the track's outward
  throw (order 10–15 cm) through the entire middle of its travel — on a component with
  severity 2.5, on the side of the van where a driver is most likely to be near a kerb or
  post. It would have produced confident wrong answers, which is worse than not modelling
  that state.

  The developer chose two scanned variants (closed / open) instead. That is strictly
  better here: R-15 already says joint states are hand-entered per run in v0.1, so if the
  state is a hand-entered label either way, a label that selects a *measured* geometry
  beats a label that drives a wrong kinematic model. Cost is no intermediate positions,
  which do not matter — nobody manoeuvres with the door half open.

  Worth noting *how* this surfaced: not from testing, but from reading the schema aloud
  against the physical object before any URDF existed. Cheap now, expensive after P2-T8.

- **The van being dark changes the R-01 reasoning, not just its number.** I had assumed
  the light-coloured failure mode (blown-out highlights). Dark maroon gloss fails the
  opposite way: the panels act like mirrors and reflect a moving scene, or go uniformly
  textureless under flat overcast. Same rating (high/high), different mitigation — the
  checklist now emphasises overlap, ground texture and extra markers rather than simply
  avoiding sun, and offers optional low-tack tape on blank panels as the developer's call.

**Decisions made (→ ADR ####):**

- **ADR 0004** — sliding door as two scanned collision variants, not a joint. `JointSpec`
  unchanged and still correct for the rear doors and mirrors, which are real hinges.
- Risk ratings agreed and recorded; re-rate at the Phase 1 gate.

**Risks touched (R-##):**
