### The geometry (P0-T3), in MAT188 terms

Written down here because the point of pair mode is that you can defend this in an
interview.

A rigid transform is a **linear map on homogeneous coordinates**. Write a point as
`p~ = [x y z 1]ᵀ ∈ ℝ⁴`, and

```
T = [ R  t ]      R ∈ SO(3),  t ∈ ℝ³        T p~ = [Rp + t, 1]ᵀ
    [ 0  1 ]
```

The appended 1 and the fourth row exist for exactly one reason: **translation is not a
linear map on ℝ³**, because it moves the origin. Lifting to ℝ⁴ makes it one, and that is
why transforms compose by plain matrix multiplication. Two things fall out and are used
everywhere in the module:

1. **Inversion is free.** `R` is orthogonal, so `R⁻¹ = Rᵀ`. Solving `q = Rp + t` gives
   `p = Rᵀq − Rᵀt`, so `T⁻¹ = [[Rᵀ, −Rᵀt], [0, 1]]`. `invert()` uses this closed form —
   `np.linalg.inv` is both slower and less accurate. The test asserts the closed form
   hits identity to 1e-14, where the generic inverse only manages ~1e-10.
2. **Order matters**, because SO(3) does not commute. The `T_a_b` naming is the guard
   rail: inner subscripts must cancel (`T_a_b @ T_b_c = T_a_c`), and numpy cannot check
   that for you, so the discipline is in every signature.

The `veh` ↔ `cam` convention is now a tested constant rather than a comment. `veh` is
x-forward / y-left / z-up, `cam` is x-right / y-down / z-forward, so

```
cam x (right)   = −veh y        R_CAM_VEH = [ 0 −1  0 ]
cam y (down)    = −veh z                    [ 0  0 −1 ]
cam z (forward) = +veh x                    [ 1  0  0 ]
```

Row *i* is the *i*-th cam basis vector written in veh coordinates, which is precisely
what makes `p_cam = R_CAM_VEH @ p_veh` true. `det = +1` is asserted — a `−1` would be a
reflection, silently swapping left and right.

  - OpenCV 5's `calibrateCamera` rejects `float64` image points — it wants `Point2f`. My

  wheel-to-kerb case is exactly 1.650 m because the wheel touches the ground, so no

  precisely 0.02 against a 0.02 gate is not evidence of meeting it. Stated in a test so
